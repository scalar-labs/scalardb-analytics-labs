# Glossary

This glossary defines the terms shared across the product documents. Each entry names the document that explains the term in context. Terms used only inside the Semantic Catalog are defined in [`semantic-catalog/glossary.md`](semantic-catalog/glossary.md), and connector terms are authoritative in the [connector documentation](https://github.com/scalar-labs/scalardb-analytics-connectors/blob/main/docs/architecture.md).

The glossary keeps names and definitions consistent and does not override the documents. When an entry and a document disagree, fix the disagreement. Aliases are abbreviations, former names, and code names, kept so that older material can still be traced.

## Knowledge in the Semantic Catalog

| Term | Code identifier | Aliases | Definition | Explained in |
| --- | --- | --- | --- | --- |
| physical schema | — | — | The tables, columns, types, and declared constraints in a source. It can be an input to data semantics but is not itself data semantics. | [`architecture.md`](architecture.md) |
| data semantics | — | — | What data represents and under which conditions data can be combined correctly. Includes row meaning, key, uniqueness, field meaning, identifier correspondence, and the business domain model. | [`semantic-catalog.md`](semantic-catalog.md) |
| analytical semantics | — | — | How business quantities are computed from data. Includes measure definitions and aggregation rules, filter conditions, the reference time and time granularity, derived classifications and calendars, and business terms. What semantic layer products such as dbt Semantic Layer, Cube, and Looker mainly define belongs to this layer. | [`semantic-catalog.md`](semantic-catalog.md) |
| closed core | — | — | The structure that the Semantic Catalog and the Query Agent interpret in common. It fixes, for each kind of element, the predicates recorded for it and the predicates Generators produce candidates for. That list says what construction aims at; it is not a set of conditions an element must meet before use. | [`semantic-catalog/record-model.md`](semantic-catalog/record-model.md) |
| Dataset | — | `Dataset` | The logical object to which meaning is given. It holds a technical reference for retrieving data but is not itself a table or view. | [`semantic-catalog.md`](semantic-catalog.md) |
| Field | — | `Field` | The logical object that gives meaning to one column in a dataset. | [`physical-catalog.md`](physical-catalog.md) |
| row meaning | — | — | The business object or event that one row of a dataset represents. It has a machine-usable structure in the closed core and may carry a natural-language description as a supplement. It is not defined as "what counting the rows gives". | [`semantic-catalog.md`](semantic-catalog.md) |
| key | — | — | The set of Fields used to identify a row of a Dataset, or "no key". | [`physical-catalog.md`](physical-catalog.md) |
| uniqueness | — | — | Whether a set of Fields repeats within a Dataset: "does not repeat" or "repeats". The Field set is part of the predicate. Whether it rests on a source declaration or on a check of the data is expressed by the validation method, not by separate predicates. Recorded and revised separately from row meaning and key. | [`semantic-catalog.md`](semantic-catalog.md) |
| business domain model | — | — | The business concepts, and the relationships between them, needed to interpret registered datasets and usage requests. Recorded as data semantics; row meaning and identifier correspondence refer to its concepts, and business terms can refer to them. Each domain's Semantic Catalog holds as much as it needs. | [`semantic-catalog/record-model.md`](semantic-catalog/record-model.md) |
| domain model | — | — | The types, and the relationships between them, held by the code of the `semantic-catalog` module. Distinct from the business domain model. | [`architecture.md`](architecture.md) |
| identifier correspondence | — | `IdentityLink` | The conditions under which values of two Field sets, in one data source or in different ones, represent the same object, and the relationship between the sets of objects each side represents. Its matching condition may normalize values with steps from a closed list. The set relationship distinguishes equal, subset, partially overlapping, and disjoint. Joining Datasets correctly rests on it; there is no separate join element, and a foreign key is a declaration that supports one. | [`semantic-catalog/record-model.md`](semantic-catalog/record-model.md) |
| Measure | — | `Measure` | The definition of a business quantity: its meaning, base Dataset, aggregation rule, filter conditions, reference time Field, and default time granularity. A period that changes per question belongs to the question, not to the Measure. | [`semantic-catalog.md`](semantic-catalog.md) |
| business term | — | `Term` | A word used in the business, recorded as its written form and the element it refers to (a Field, Measure, concept, or other element). | [`semantic-catalog.md`](semantic-catalog.md) |

## Statements and records

| Term | Code identifier | Aliases | Definition | Explained in |
| --- | --- | --- | --- | --- |
| statement | — | — | A claim that a certain value holds for one property of one object. | [`application.md`](application.md) |
| URN | `Urns`, `Ref` | Uniform Resource Name | The name, in one system, for referring to catalog elements (nodes and edges), Fact Addresses, Facts, Fact Revisions, Input Resources, Input Observations, and Catalog Snapshots. It is issued at creation, is unique, never changes, is never reused, and carries no content. Whether two things are the same is not decided from URNs. The domain comes first. | [`semantic-catalog/record-model.md`](semantic-catalog/record-model.md) |
| Fact Address | `LogRecord.FactAddress` | — | What identifies, independently of any value, what is being judged: an element, a predicate, and the applicability scope within which values are compared. Like every record, it has its own URN, which carries none of its content. | [`semantic-catalog.md`](semantic-catalog.md) |
| Fact | `LogRecord.Fact` | — | An immutable statement that binds a value to the applicability scope of one Fact Address. Different values for the same Fact Address are different Facts, not revisions of one Fact. | [`architecture.md`](architecture.md) |
| Fact Record | `FactRecord` | — | How the Semantic Catalog currently treats one Fact, obtained by applying the Fact Events concerning that Fact in order. Derived from the log, it is expressed as a state machine and links the Fact's state, validation results, provenance, dependencies, and deciding party. | [`semantic-catalog.md`](semantic-catalog.md) |
| Fact Event | `LogRecord.FactEvent` | — | An event, with its reason, that changes how a Fact is treated, such as accepting a candidate, an additional acceptance, consent, rejection, refutation, or an update proposal. It is written to the log, and one event can affect several Facts. Selections determined by rule are not recorded; they are derived from the log. | [`semantic-catalog.md`](semantic-catalog.md) |
| Fact Revision | `FactRevision` | — | The immutable version of a Fact Record after each Fact Event is applied. Derived from the log, it has a URN so that dependency references can point to it. It refers to the preceding Fact Revision and to the Fact Event that caused the change. | [`application.md`](application.md) |
| Input Resource | `LogRecord.InputResource` | input resource | A source of input whose changes are tracked over time. A physical schema and a document registered by a semantics owner are each treated as an Input Resource. | [`semantic-catalog/record-model.md`](semantic-catalog/record-model.md) |
| Input Observation | `LogRecord.InputObservation` | input observation | The content of an Input Resource as observed at a point in time. | [`semantic-catalog/record-model.md`](semantic-catalog/record-model.md) |
| dependency reference | `Dependency` | Input Reference | The reference by which a Fact Revision indicates what it depends on. A dependency on an input holds the URN of the Input Resource, used to look for changes, and the URN of the Input Observation actually used. A dependency on another Fact holds the Fact's URN and the Fact Revision actually used; it is a premise dependency when that Fact is at another Fact Address and a replacement dependency when it is at the same one. Only premise dependencies gate confirmation and cascade rejection and retirement. | [`semantic-catalog/record-model.md`](semantic-catalog/record-model.md) |
| provenance | — | — | Who or what entered or judged something, when, and by which method. | [`application.md`](application.md) |
| applicability scope | `Scope` | — | Which questions, objects, conditions, and periods a piece of knowledge applies to. Expressed as a natural-language description paired with URN references to the entities it mentions. Values that are correct at the same time in different applicability scopes are not treated as a conflict. When scopes overlap, the Query Agent judges which Fact to use. | [`semantic-catalog.md`](semantic-catalog.md) |
| Catalog Snapshot | `CatalogSnapshot` | — | The domain's whole catalog constructed from the log up to a point in time. There is no operation that creates one; because it is determined uniquely from the log for each point, the Catalog Snapshot of a point does not change. For each Fact Address it selects at most one Fact among the confirmed Facts presentable at that point and indicates that Fact's Fact Revision at that point. A new Fact that cannot yet be presented does not displace the Fact selected until then. | [`architecture.md`](architecture.md) |
| semantic presentability | — | — | The judgement of whether knowledge may be presented to consumers. It is determined by whether, within a Catalog Snapshot, the validation results, provenance, deciding party, and applied user policy can be traced from the confirmed Fact's Fact Revision, the judgement its user policy requires is complete, and the Facts it depends on are presentable in the same Catalog Snapshot; and, at request time, by whether it applies to the requested target and conditions. It does not include whether the using party may access the knowledge. | [`semantic-catalog/catalog-snapshot.md`](semantic-catalog/catalog-snapshot.md) |
| missing knowledge | `Knowledge.MissingKnowledge` | — | The situation in which requested knowledge has neither a confirmed Fact nor an accepted candidate. | [`architecture.md`](architecture.md) |
| awaiting judgement | `Knowledge.AwaitingJudgement` | — | The status of requested knowledge whose Fact Address has no eligible Fact but has `candidate` Facts, including candidates waiting for the Facts they depend on to be confirmed. | [`semantic-catalog.md`](semantic-catalog.md) |
| conflict | `Knowledge.Conflict` | — | The situation in which incompatible confirmed Facts presentable at the same Fact Address do not include each other in their dependency references and await a conflict resolution. A previously selected Fact, if any, stays selected. The semantics owner or a delegate resolves it, recording a `resolve-conflict` that names the chosen and passed-over Facts. | [`semantic-catalog/catalog-snapshot.md`](semantic-catalog/catalog-snapshot.md) |
| replacement | — | — | Switching the selection to a presentable confirmed Fact when it includes, in its dependency references, the Fact selected for the same Fact Address. The basis is not time but the dependency: the new Fact was made taking the previous one into account. | [`semantic-catalog/catalog-snapshot.md`](semantic-catalog/catalog-snapshot.md) |
| trace record | — | usage record | A record that groups the sequence of use for one question: its receipt, the queries to each component, the Catalog Snapshot read, the knowledge used, the query composed and its execution, and the user's acceptance or correction. Held by the module that traces application-wide use. Stored separately from the Fact log, never received by the Semantic Catalog, and never used as evidence that knowledge is correct. | [`architecture.md`](architecture.md) |
| correctness | — | — | One quality axis: whether confirmed knowledge and the results of using it are correct. | [`semantic-catalog.md`](semantic-catalog.md) |
| load | — | — | One quality axis: how much judgement, correction, and re-confirmation work falls on the semantics owner or a delegate. | [`physical-catalog.md`](physical-catalog.md) |
| traceability | — | — | One quality axis: whether construction judgements (deciding party, inputs, validation results, provenance) and the flow of use (which knowledge was used for which question, and with what outcome) can be traced. The product always provides the means to trace use, the user organization chooses what is acquired, and what is acquired supports after-the-fact evaluation. Construction learns from use through usage feedback instead. | [`semantic-catalog.md`](semantic-catalog.md) |

## Construction process

| Term | Code identifier | Aliases | Definition | Explained in |
| --- | --- | --- | --- | --- |
| Generator | — | — | The function that takes physical schemas, data observations, existing knowledge, external documents, and similar inputs and produces knowledge candidates with their validation results. Acceptance, presentation, judgement, and confirmation are not its responsibility, and it has no authority to confirm a candidate. | [`architecture.md`](architecture.md) |
| impact judgement | — | — | The process in which an LLM judges whether a new observation of a physical schema or a document affects existing Facts, and selects the Facts to re-examine. | [`semantic-catalog/construction.md`](semantic-catalog/construction.md) |
| usage feedback | — | — | What a user's LLM session finds worth keeping as knowledge outside review, including missing knowledge met while composing a query, and the wording of corrections given in review. It holds its content, the session's purpose (composing a query or constructing the catalog), a summary of the session's context, and optionally related Facts. Each registration is a new Input Resource. It is recorded as an Input Observation and is a Generator input; it is not a command to replace the selected Fact. | [`architecture.md`](architecture.md) |
| validation result | `List<Check>` | — | What one or more checks found for a candidate: for each check, the validation method, the validation items it covered, a result of supported, refuted, or undecidable, and the input it was checked against. The range that could not be confirmed is computed from it. Recorded in a Fact Event and referenced from a Fact Revision. | [`architecture.md`](architecture.md) |
| raw candidate | — | — | A statement produced by a Generator, before acceptance. | [`semantic-catalog/construction.md`](semantic-catalog/construction.md) |
| accepted candidate | — | — | A raw candidate accepted as a Fact and handled as a candidate in a Fact Record. | [`semantic-catalog.md`](semantic-catalog.md) |
| confirmation | — | — | Making an accepted candidate into confirmed knowledge. From the point where it becomes presentable together with the Facts it depends on, it is presented in later Catalog Snapshots, and the Query Agent can then use it. Whether it is selected, replaces another, or conflicts follows the selection rules. | [`application.md`](application.md) |
| confirmed knowledge | — | — | A Fact that has completed the judgement its user policy requires. Whether it is presented to consumers is determined by semantic presentability. | [`architecture.md`](architecture.md) |
| unconfirmed knowledge | — | — | Accepted candidates, answers from a user who is not a deciding party, and assumptions made by the Query Agent. Usable for composing a query only when the user explicitly asks, and the result states which knowledge was unconfirmed. | [`semantic-catalog.md`](semantic-catalog.md) |
| user policy | `LogRecord.PolicyVersion` | — | The rule that decides, when an accepted candidate becomes confirmed knowledge, whether machine judgement alone confirms it or the consent of the semantics owner or a delegate is required. The domain's semantics owner sets it, and each change is recorded as a new version. | [`architecture.md`](architecture.md) |
| machine judgement | — | — | Confirmation by automatic evaluation, without requesting human consent. | [`architecture.md`](architecture.md) |
| human consent | — | — | The path of confirming by requesting and obtaining the consent of the semantics owner or a delegate. | [`semantic-catalog/record-model.md`](semantic-catalog/record-model.md) |
